# Telemetry receiver

`ingestTelemetry` is the server-only entry point for equipment readings. Devices
do not sign in to Firebase and never receive Firestore permissions.

## HTTP contract

Send `POST` JSON with `Authorization: Bearer <device key>`:

```json
{
  "deviceId": "device-001",
  "packetId": "boot-a:000001",
  "measurements": [
    { "measuredAt": "2026-09-13T01:00:00.000Z", "temperatureC": -18.5 },
    { "measuredAt": "2026-09-13T01:00:10.000Z", "temperatureC": -18.4 }
  ]
}
```

`packetId` must remain unique for that device across retries. A successful new
packet returns HTTP 202; an already stored packet returns HTTP 200 with
`duplicate: true`. Both timestamps are retained: `measuredAt` from the device
and `receivedAt` generated by the server.

The bearer key must only be sent over a transport whose TLS support has been
verified on the actual SIM900A/firmware/operator path. Plain HTTP is used only
for the loopback emulator test and is not an acceptable field transport.

## Firestore layout

- `monitoringDevices/{deviceId}`: registry, enabled flag and assignment fields
  such as `clientId`, `targetType` (`vehicle` or `chamber`) and `targetId`.
- `monitoringDeviceCredentials/{deviceId}`: revocable `active` flag plus the
  salted scrypt hash. Firestore rules deny all client access.
- `monitoringDeviceState/{deviceId}`: latest reading and last packet receipt.
- `monitoringTelemetry/{deviceId}/packets/{packetId}`: packet history. It is
  nested deliberately so CRM screens query one device and a bounded time range
  instead of subscribing to all history.

Generate a new random key and its credential document without writing either to
disk:

```powershell
npm run generate:device-key -- device-001
```

Store only `credentialDocument` in Firestore and transfer `deviceKey` through a
secure provisioning channel. Revoke it by changing `active` to `false`; rotate
it by replacing the credential document with a newly generated hash.

## Emulator check

Build before starting the Functions emulator because it loads `lib/index.js`:

```powershell
npm --prefix functions run build
firebase emulators:exec --only firestore,functions --project demo-coolservice-crm "npm --prefix functions run test:emulator"
firebase emulators:exec --only firestore --project demo-coolservice-crm "npm --prefix web run test:rules"
```

The `demo-` project ID prevents accidental fallback to the production project.

## Local CRM screen

Build Functions, then keep the three emulators running in the first terminal:

```powershell
npm --prefix functions run build
firebase emulators:start --only auth,firestore,functions --project demo-coolservice-crm
```

Seed clearly labelled demo devices in a second terminal. The seed uses only
localhost emulator addresses and sends the main device history through
`ingestTelemetry`:

```powershell
npm --prefix functions run seed:monitoring-demo
```

Start Vite in the same terminal and open `http://127.0.0.1:5173/`:

```powershell
$env:VITE_USE_FIREBASE_EMULATORS="true"
npm --prefix web run dev -- --host 127.0.0.1 --port 5173
```

Demo logins created by the seed:

- manager: `monitoring.manager@example.test` / `DemoMonitor123!`
- mechanic: `monitoring.mechanic@example.test` / `DemoMonitor123!`
