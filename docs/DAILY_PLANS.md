# ППЗ — персональные планы сотрудников

## Использование

В разделе «ППЗ» сотрудник открывает «Мой день». Руководитель (owner/admin/manager)
открывает «Планёрка», выбирает дату и сотрудника. Добавляет уже назначенные работы
из ремонтов, приёмки или сервисных задач; новые хозяйственные работы создаются
как `servicetasks` при сохранении черновика. До 50 пунктов на сотрудника и дату.
Руководитель задаёт порядок, приоритет, время и примечание, сохраняет черновик
и публикует его. Публикация каждого сотрудника создаёт отдельное сообщение в группе;
длинные планы отправляются несколькими последовательными сообщениями.

Черновик не заменяет опубликованный план. Выполнение и комментарии сохраняются
в исходной задаче, включая отдельный `doneBy` каждого исполнителя общей работы.
Комментарий сам по себе не меняет статус. План показывает записи сотрудника
на приём отдельно от задач. Нерабочие дни из `schedules` выводятся как предупреждение.
Даты и время плана относятся к `Asia/Vladivostok`.

Перенос: выбрать следующий день и добавить ту же незавершённую исходную задачу.
Снятие пункта из плана не удаляет задачу. Удалённые/перемещённые задачи, включая
закрытую приёмку, требуют корректировки плана руководителем. Автопереноса и
автопубликации нет. Голосовой помощник и личные Telegram-сообщения в этот этап не входят.

## Данные и доступ

- `dailyPlans/{staffId}_{YYYY-MM-DD}`: staffId, date, revision, version,
  status (`draft`/`published`), hasDraft, авторы/время, deliveryStatus.
- `draftItems/{itemId}`: рабочий черновик, доступен только руководителю.
- `items/{itemId}`: опубликованные пункты, доступны руководителю и своему сотруднику.
  Поля: source (kind/documentId/repairId/taskId), title, order, priority, deadline, note.
- `dailyPlanNotifications/{planId}_{version}_{recipient}_{part}`: неизменяемый снимок текста,
  получатель, номер части, статус/попытки, Telegram messageId после успеха.

Все записи ППЗ и очереди доступны только серверу. Callable-функции проверяют Auth,
роль и исполнителя исходной задачи. Сохранение и публикация используют транзакции
и ожидаемую revision, поэтому параллельные правки не перезаписываются молча.
Сотрудник меняет только свою отметку выполнения, состав плана менять не может.
Правила сервисных задач дополнительно защищают верхнеуровневые поля назначения
и сохраняют `doneBy` других исполнителей при клиентских обновлениях.
Существующие правила массивов клиентских ремонтов и приёмки в рамках этого этапа
не переработаны; их прежний широкий доступ остаётся отдельным ограничением CRM.

## Доставка Telegram

Новые функции размещаются в `europe-west1`:
`saveDailyPlan`, `publishDailyPlan`, `updateDailyPlanWork`,
`retryDailyPlanNotification`, `notifyDailyPlanPublished`, `retryDailyPlanDeliveries`.

Используются существующие секреты `TELEGRAM_BOT_TOKEN` и `TELEGRAM_GROUP_CHAT_ID`:
ППЗ приходит в те же группы через того же бота, что и уведомления по заявкам.
Новый секрет или повторный ввод ID не требуется. Если в настройке несколько групп
через запятую, каждая получает план, повторяющиеся ID исключаются. Личные получатели
из `TELEGRAM_CHAT_ID` для ППЗ не используются. Результат доставки учитывается
отдельно для каждой группы. Значения секретов не хранить в Git.

Очередь атомарно создаётся при публикации. Временные явные отказы Telegram (429/5xx)
повторяются с задержкой, до пяти попыток. Сетевой сбой или неразбираемый ответ
помечается `unknown`: сообщение могло дойти. Такие попытки автоматически не повторяются.
Отправка, прерванная более пяти минут назад, также становится `unknown`.
Руководитель проверяет группу и вручную повторяет проблемные сообщения через экран ППЗ.
Это может создать дубль; абсолютная гарантия единственной доставки отсутствует.
Новые версии отменяют ещё не начатую отправку старых версий; уже отправленные
или находящиеся в процессе сообщения не удаляются. Часть с большим номером
ждёт успешной доставки предыдущей части. Плановая проверка очереди — раз в минуту.
Функции используют только текст, без Telegram Markdown, поэтому пользовательский
текст не интерпретируется как разметка. Старые уведомления ремонтов не меняются.

## Запуск в рабочей системе

1. Использовать сохранённые `TELEGRAM_GROUP_CHAT_ID` и `TELEGRAM_BOT_TOKEN`.
   Убедиться, что бот по-прежнему может писать в существующую группу.
2. Развернуть Firestore rules и indexes; дождаться готовности индекса
   `dailyPlanNotifications(status, nextAttemptAt)`.
3. Развернуть только шесть новых функций, перечисленных выше, чтобы не публиковать
   попутно изменения других функций. Требуется доступный проект Firebase с Blaze.
4. Опубликовать web-сборку обычным способом проекта.
5. Проверить одним тестовым планом в выбранной группе и сверить статус доставки в CRM.

## Проверки

`npm --prefix web run typecheck`, `npm --prefix web run build`,
`npm --prefix functions run test:daily-plans`.

Firestore emulator:

```text
firebase emulators:exec --only firestore --project demo-coolservice-crm "npm --prefix web test && npm --prefix functions run test:daily-plans:emulator"
```

Интеграционные тесты используют Admin SDK только с `FIRESTORE_EMULATOR_HOST`,
поддельные секреты и подменённый Telegram HTTP. Проверяют права, атомарность,
конкурентные правки, смену исполнителей, совместное выполнение, вложенные задачи,
пустой день, повторную публикацию, неопределённую доставку и порядок частей.
CI запускает эти проверки отдельно от существующих тестов CRM.

## Локальный UI-пример

Запустить Auth и Firestore emulators для `demo-coolservice-crm`.
Задать `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080` и
`FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9099`, затем
`npm --prefix functions run seed:daily-plan-demo`.
Скрипт отказывается работать без обоих эмуляторов.
Запустить Vite с `VITE_USE_FIREBASE_EMULATORS=true`.

Тестовые логины: `ppz-manager@example.test`, `ppz-worker@example.test`;
пароль обоих `DemoPPZ2026!`. Это исключительно локальные тестовые аккаунты.
Для отображения планов Functions emulator не требуется; для сохранения через UI
нужен также Functions emulator. Доставка в UI-примере отмечена как тестовый снимок,
реальные Telegram-сообщения seed-скрипт не отправляет.
