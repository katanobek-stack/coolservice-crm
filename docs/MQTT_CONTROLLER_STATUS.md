# Диагностика GSM/MQTT-контроллера

Этот контракт предназначен для отдельного сообщения диагностики. Он не
изменяет температурный MQTT-пакет, `ingestTelemetry` или дедупликацию
измерений по `packetId`.

## MQTT-сообщение

Тема строго сопоставляется с идентификатором в payload:

```text
coolmonitor/devices/{controllerId}/status
```

Для `device-001` тема: `coolmonitor/devices/device-001/status`.
Публикация должна использовать MQTT QoS 1. `statusId` — стабильный уникальный
идентификатор одного события (например, идентификатор загрузки контроллера и
счётчик); повторная публикация того же события обязана сохранить тот же ID.

```json
{
  "controllerId": "device-001",
  "statusId": "boot-123:42",
  "reportedAt": "2026-09-17T01:23:45.000Z",
  "networkRegistered": true,
  "registrationState": "home",
  "rssi": 21,
  "gprsConnected": true,
  "mqttConnected": true,
  "queueDepth": 0,
  "lastFailureCode": "none",
  "uptimeSeconds": 3600
}
```

Все поля обязательны. `reportedAt` — ISO-8601 UTC с суффиксом `Z`; сервер
принимает время не более чем на 10 минут в будущем и не старше 7 суток. Поля
`queueDepth` и `uptimeSeconds` — неотрицательные целые числа. `rssi` — целое
от 0 до 31 либо `null` при отсутствии доступного значения.

Допустимые `registrationState`: `home`, `roaming`, `searching`, `denied`,
`unknown`.

Допустимые `lastFailureCode`: `none`, `modem_not_ready`,
`network_not_registered`, `ntp_sync_failed`, `gprs_connect_failed`,
`tcp_connect_failed`, `mqtt_connect_failed`, `publish_send_failed`,
`puback_timeout`, `modem_restarted`, `esp_restarted`.

## Требуемое изменение crm-mqtt-bridge

Исходники bridge не находятся в этом репозитории, поэтому его конфигурация и
исполняемый код здесь намеренно не менялись. При его доработке bridge должен:

1. Подписаться только на `coolmonitor/devices/+/status` в отдельном обработчике.
2. Проверить, что `controllerId` из JSON равен сегменту темы, и отклонить
   неизвестные поля, неверные типы и перечисления до пересылки.
3. Не преобразовывать status в температурный пакет и не публиковать его в
   `ingestTelemetry`.
4. Пересылать неизменённое тело JSON через HTTPS POST в `ingestControllerStatus`
   с существующим защищённым механизмом предоставления ключа устройства bridge.
   Ключ не помещается в MQTT payload, не логируется и не передаётся по HTTP.
5. Считать HTTP 202 успешным приёмом, а HTTP 200 успешной дедупликацией;
   повторять только временные ошибки. HTTP 400/401 не повторять бесконечно и
   журналировать без заголовка Authorization и без полезных секретов.

`ingestControllerStatus` использует тот же отзываемый credential-document, что
и температура, но отдельное `statusId`-хранилище. Поэтому bridge не должен
создавать или читать Firestore-документы напрямую.

## Хранение и идемпотентность

- Текущее состояние: `monitoringControllerStatus/{controllerId}`.
- История: `monitoringControllerStatus/{controllerId}/statusEvents/{statusId}`.
- Один `statusId` создаёт не более одного документа истории. Повтор возвращает
  HTTP 200 и не меняет текущий статус.
- Более поздний по `reportedAt` статус обновляет текущий документ. Отложенный
  статус остаётся в истории, но не откатывает текущую связь.
- Истории назначается `expireAt` через 7 дней. Для фактической очистки перед
  публикацией следует отдельно включить Firestore TTL для collection group
  `statusEvents`, поле `expireAt`. До включения TTL история не удаляется
  автоматически.

Браузер читает только текущие документы для списка. История статусов не входит
в общую подписку. Запись обоих путей разрешена только Cloud Function через
Admin SDK; устройства и браузер не имеют доступа на запись.

## Отображение свежести

Порог берётся из `settings/monitoring.offlineThresholdMinutes`, по умолчанию
5 минут. Это тот же настраиваемый порог, что показывает интерфейс CRM.

- **На связи**: последний текущий status по `reportedAt` не старше порога.
- **Связь потеряна**: status был, но его `reportedAt` старше порога.
- **Статус связи не получен**: controller status пока не было.
- **Температура устарела** определяется отдельно по `measuredAt` температурного
  состояния. Новый status не делает старое измерение актуальным; отложенная
  температура также не меняет свою временную метку.

CRM показывает локальное время пользователю, а сервер сохраняет timestamp в
UTC. В карточке время status и время его получения сервером выводятся отдельно.
