# Общие задачи ППЗ без сроков

## 2026-10-21 — новые общие задачи сверху

Списки активных и завершённых общих задач ППЗ сортируются по серверному
createdAt от новых к старым, в том числе после фильтра по сотруднику. Изменение
отчёта или статуса не меняет дату создания и не поднимает старую задачу.
При одинаковой дате используется стабильный порядок ID; документы без даты
не пропадают, остаются внизу. Сортируется копия уже полученного snapshot:
дополнительных чтений, индексов, записей или миграций нет. Ручной порядок
дневного плана (order) не меняется. Проверки: typecheck, 93 unit-теста,
production build и git diff --check — успешно. Пользователь подтвердил выпуск
через commit/push/PR/CI и Pages; Functions, Rules и VPS не меняются.

## 2026-10-21 — диктовка личного отчёта (локально)

В личных отчётах общих задач и комментариях дневного плана добавлена большая
кнопка «Надиктовать отчёт» / «Остановить диктовку». Используется браузерный
SpeechRecognition, язык ru-RU, максимум 60 секунд. Это не командный агент:
parseVoiceCommand/Anthropic не вызываются, CRM-записи сами не создаются.
Только окончательные результаты добавляются к текущему черновику, повторные
результаты не дублируются. Текст остаётся редактируемым после остановки;
сохранение вручную, во время записи запрещено. Лимиты 2000/1000 символов
сохранены, при обрезании показывается предупреждение. Фото и права не меняются.

Микрофон включается только по нажатию и с разрешения браузера. Одновременно
активен один отчёт; при уходе со страницы/скрытии вкладки запись прерывается,
поздние результаты игнорируются. Без поддержки API, при отказе доступа,
ошибке сети или микрофона доступен обычный ввод. Ошибки не стирают черновик.
При stop ожидается финальный результат до 3 секунд, затем принудительный abort.
Промежуточные результаты не сохраняются. Аудио в CRM/Storage не загружается,
но сервис браузера может передавать звук своему провайдеру; пояснение есть в UI.
Поддержка конкретного браузера/системы и интернет необходимы; работа офлайн
не гарантирована. Functions, Rules, индексы, прошивка и VPS не меняются.
По следующему подтверждению пользователя подготовлен общий выпуск через
commit/push/PR/CI и Pages. Серверные функции для диктовки менять не нужно.
Общий компонент shared/ui/ReportText подключён также в WorkCommentModal:
отчёты задач приёмки, заявок, самостоятельных сервисных задач и подзадач.
Кнопки «Отчёт» и «Изменить» открывают прежнее окно с добавленной диктовкой.
Существующий текст загружается целиком (в том числе старые отчёты длиннее
2000 символов), диктовка его дополняет. Ошибка сохранения не закрывает окно,
текст остаётся для повторной попытки. Права, пути Firestore, фото и сохранение
workComment прежние. Стили общие, не зависят от открытия вкладки ППЗ.

Локальные проверки: web typecheck, все 91 unit-тест, production build и
git diff --check прошли. В тестах — дополнение черновика, дедупликация final,
stop/final/end, отказ доступа/сеть/микрофон/тишина, retry, смена отчёта,
поздний callback, исключение start, лимит 60 секунд и принудительная очистка.
Браузерный тест с имитацией SpeechRecognition подтвердил добавление текста,
блокировку сохранения и редактирования при записи, восстановление после stop
и отказа доступа. При 390 px горизонтального переполнения нет; кнопка 62 px.
Настоящий микрофон/внешний speech-сервис на телефоне этим тестом не проверялись.
Общее окно отчёта задачи отдельно проверено в браузере: диктовка дополняет
старый текст, save заблокирован до stop, ошибка save оставляет окно и текст,
повторное сохранение успешно. На ширине 390 px форма не переполняется.
Тесты подтверждают общий маршрут кнопок приёмки/заявок/сервисных подзадач и
сохранность длинных старых отчётов. Firebase/Rules/VPS не нужны для выпуска.

## 2026-10-21 — фото выполнения и цветовые группы (локальная подготовка)

Проверки локально: web typecheck, 81 web unit-тест, functions build и 12
серверных unit-тестов, production web build, git diff --check — успешно.
SSR-превью реальных карточек проверено в браузере на desktop и 390 px:
горизонтального переполнения нет. Добавлены интеграционные тесты прав,
повторных запросов и сохранения фото в исходной задаче/истории. Их локальный
запуск остановлен CLI: `Could not spawn java -version`; Java отсутствует.
До публикации необходимо запустить Firestore Emulator (например, штатный CI).

К своему отчёту можно выбрать до 6 изображений (камера/галерея), предварительно
убрать лишние. Загрузка в существующий Firebase Storage выполняется при
сохранении, с прежним сжатием JPEG, а не при каждом выборе. Успешно загруженные
файлы повторно используются после сетевой ошибки. Текст первого личного
отчёта по-прежнему обязателен; к существующему результату можно добавить фото.
Фото хранятся в `work-reports/{uid}/ppz/{taskId}/...jpg` либо
`work-reports/{uid}/plan/{planId}/{itemId}/...jpg`. До 60 фото на работу/участника.
В Firestore сохраняются только ссылки, не изображения/base64. Сервер проверяет
UID, назначение, собственный опубликованный план, префикс пути и bucket проекта;
произвольные внешние URL, чужой UID и дубли отклоняются. Неизвестные поля
метаданных не считаются доказательством автора.

Общие задачи сохраняют снимки фото в participants/{uid} и неизменяемых
workEvents. Уточнение дополняет фото, не стирает старые и не начисляет новое
выполнение. Дневной план дополняет photos исходной задачи ремонта/приёмки/сервиса
и пишет отдельное `photo_added` от аутентифицированного сотрудника. Квитанция
dailyPlans/{planId}/photoRequests защищает фотоотчёт от повторной отправки,
включая комментарий. Фото-событие не прибавляет завершений; автор и время
фиксируются сервером. Журнал не удаляется при переносе исходного ремонта.

В «Учёт работ и история» доступны снимки, «Работ с фото» и «Фотографий» по
сотруднику и периоду. Повторы ссылок считаются один раз. Фото — отдельный
показатель, не дополнительное выполнение и не оценка качества. CSV содержит
число фото, но не публичные download-token ссылки. На дашборде этот же учёт
открывается по кнопке только для admin/owner: новая подписка не создаётся до
открытия панели. Права и запросы workEvents не расширены.

Цветные подписи сотрудников стабильны по UID. Статусы задач дублируются
текстом: янтарный — к выполнению, синий — в работе, зелёный — выполнено.
Личная отметка не смешивается с общим закрытием.

Нужен отдельный подтверждённый выпуск только savePpzTask, updateDailyPlanWork
и web Pages. Rules/indexes, Storage Rules, Telegram, VPS и прошивка не меняются.
Production-записи, миграции, commit/push и deploy на этом этапе не выполнялись.
Ограничение существующего хранилища: Storage Rules уже разрешают публичное
чтение по URL. Новая функция не делает фотографии приватными. При обрыве до
фиксации отчёта возможны загруженные, но ещё не привязанные файлы: они не
удаляются автоматически, чтобы не удалить уже подтверждённый сервером снимок.

Блок «Задачи без сроков» находится в ППЗ над существующим дневным планом.
Администратор и владелец назначают общую задачу одному или нескольким
существующим сотрудникам и видят все задачи с фильтром по сотруднику.
Сотрудники видят только свои назначения. «Приступить» фиксирует начало работы.
«Завершить для всех» убирает задачу из активных списков всех исполнителей,
сохраняя её в завершённых вместе с автором и серверным временем закрытия.
Повторный или одновременный запрос сохраняет первого закрывшего.

Документ ppzTasks/{id} хранит общий статус и массив assignees. Из браузера
доступно только чтение по правилам Firestore; изменения проходят через
savePpzTask в europe-west1. Менять статус может только назначенный исполнитель.
Прежние дневные планы, Telegram и задачи ремонта не меняются.

## Разовый перенос из ClickUp

scripts/import-ppz-tasks.js в functions принимает путь к локальному JSON:
projectId, meetingDate, nameMapping (имя -> существующий UID), tasks
(id, title, assignees как массив имён, taskId и необязательные commentId/description).
По умолчанию выполняется проверка без записи. Для записи нужны --execute
и --project=coolservice-crm. Сценарий проверяет реальные профили, атомарно
создаёт документы и сохраняет ссылку на источник. Повторный запуск не
перезаписывает существующие задачи, их статусы и отметки выполнения.
Назначения следует брать также из комментариев ClickUp: поле assignees
может быть пустым, хотя решение планёрки уже записано текстом.
ClickUp этим сценарием не изменяется.

## Учёт выполнения для будущего KPI

Каждый участник ППЗ может нажать «Приступить к работе», затем описать свой
результат и зафиксировать личное выполнение. «Завершить для всех» сохраняет
общее закрытие отдельно: без автоматического начисления выполнения остальным.
Участник может добавить свой результат после общего закрытия. Уточнение отчёта
сохраняет предыдущий текст в журнале; конкурирующие уточнения защищены revision.
Идентификатор запроса защищает от повторной записи при сетевом повторе.

workEvents хранит неизменяемые события с sourceKind, стабильным workKey,
staffId (за кого сделана отметка), actorId (кто изменил данные), временем
исходного изменения occurredAt и серверным recordedAt, типом и текстом.
ППЗ пишет журнал в той же транзакции. auditRepairWork, auditIntakeWork и
auditServiceWork следят за clients, intakeRepairs и servicetasks, включая
сервисные подзадачи. Они записывают изменения doneBy, общего статуса,
рабочего комментария и создание приёмки автомобиля. События идентифицируются
по ID исходного события: повторная доставка не дублирует историю. Порядок
прихода не используется для порядка выполнения.

Перенос ремонта из приёмки к клиенту сохраняет workKey repair/{repairId}/task/{id}
и не создаёт нового выполнения. Удаление intake-документа не удаляет журнал.
Камеры не увеличивают счётчик принятых машин. Новые уже завершённые документы
и задачи не считаются выполненными заново: история до подключения не выдумывается.

Для прямых записей ремонта автор берётся из Auth Context триггера и сверяется
с staff. Отметка за другого сотрудника или запись серверным процессом сохраняется
отдельно, с selfReported=false. Значения createdBy/editedBy из клиентского
документа не используются как доказательство авторства. Существующий
updateDailyPlanWork пишет от служебного аккаунта, поэтому его изменения
ремонтных/сервисных задач попадут в наблюдения без подтверждённого личного автора.
Старые широкие правила массивов ремонта не ужесточаются этим выпуском;
журнал фиксирует действия, а не подтверждает качество или фактическую выработку.

Руководители открывают «Учёт работ и история» в ППЗ, выбирают период, сотрудника
и тип работ. Сводка считает разные факты отдельными колонками, журнал доступен
для выгрузки CSV. Даты относятся к Asia/Vladivostok. Все события периода загружаются
до расчёта сводки; ограничение отображения карточек не обрезает итог и экспорт.
Повторные личные отметки одной задачи в периоде не увеличивают число работ,
а последняя отмена исключает её из личных выполнений этого периода.
Приёмка и закрытие — отдельные показатели, они не суммируются в единый балл.
Оценки качества, утверждения руководителем, часы работы, веса и формула KPI
пока не добавлены. Длительность между кликами не равна отработанному времени.

Для выпуска обновляются только firestore:rules, savePpzTask, auditRepairWork,
auditIntakeWork, auditServiceWork и интерфейс. Существующие задачи не мигрируются
и не закрываются. Серверные тесты учёта входят в test:daily-plans и
test:daily-plans:emulator; web-агрегации — в test:unit.
