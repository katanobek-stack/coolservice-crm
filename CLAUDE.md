# Инструкции для Claude Code

## Проект
CRM-система для рефрижераторного сервиса RefServiceDV (Владивосток).
Репозиторий: `coolservice-crm`.

## Правила работы
- Читай только папки `src/`, `web/src/` и `functions/src/`, если пользователь явно не расширил область задачи.
- Не читай `node_modules`, `.git`, `dist`, `build`, `functions/lib`.
- Не делай commit или push без явного разрешения пользователя.
- В начале каждой сессии проверяй последний коммит и `git status`.
- Перед push проверяй вызовы `.split()` и `.map()` на возможность `undefined`.
- Не меняй несвязанные пользовательские изменения в рабочей копии.

## Стек
React + TypeScript + Vite + Firebase + Tailwind CSS.

## Фактическая архитектура (август 2026)

### Клиентское приложение
- SPA без URL-роутера: текущая вкладка хранится в состоянии `AppShell`.
- `web/src/app/` — инициализация Firebase, auth gate, error boundary, desktop/mobile navigation.
- `web/src/shared/` — типы, Firebase CRUD, realtime-контекст, разрешения, фото, форматирование и FCM.
- `web/src/features/` — функциональные модули CRM.
- Корневая папка `src/` сейчас пустая.

### Данные Firestore
`DataProvider` подписывается в реальном времени на:
- `clients` — клиенты; внутри документов находятся массивы `vehicles`, `chambers`, `repairs`, а внутри ремонтов — `tasks` и `photos`;
- `staff` — сотрудники и роли;
- `servicetasks` — самостоятельные сервисные задачи и проекты;
- `freezers` — склад камер и аренда;
- `settings/finance` — финансовые настройки;
- `expenses` — комиссии и прочие расходы;
- `appointments` — глобальные записи на приём.

Большинство операций с ремонтом перезаписывают целиком массив `clients/{id}.repairs`. Это важно учитывать при параллельной работе нескольких пользователей.

### Cloud Functions
- `functions/src/` — Cloud Functions Node 20, TypeScript, `firebase-functions` v2.
- Триггеры `onCreate/onUpdate` работают на `clients/{clientId}`, потому что ремонты, задачи и фото хранятся вложенными массивами.
- Telegram-секреты задаются через `firebase functions:secrets:set`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_GROUP_CHAT_ID`.
- Получатели: личные chat id из `TELEGRAM_CHAT_ID` плюс группа из `TELEGRAM_GROUP_CHAT_ID`.
- Уведомления: новая заявка, новая задача, закрытие задачи, фото к задаче, закрытие заявки.
- Завершение задачи определяется так же, как в web: `status === "done"` либо все `assignees` входят в `doneBy`.

## Основные реализованные модули
- Авторизация Firebase, профили и роли `owner/admin/manager/mechanic`.
- Дашборд: KPI, активные ремонты, выручка, расходы, рейтинг механиков, расход фреона.
- Физлица и компании: поиск, карточки, перевод физлица в юрлицо.
- Автомобили: тип транспорта, фото, марка/номер и отдельная история ремонтов.
- Производственные камеры клиентов.
- Ремонты: создание, редактирование, исполнители, задачи, комментарии, фото и закрытие с суммой.
- Автоматическая задача «Заправка фреона» при создании каждого ремонта.
- Самостоятельные сервисные задачи, проекты и подзадачи.
- Глобальные записи на приём: создание, редактирование, закрытие, отказ и преобразование в ремонт.
- График сотрудников: выходные, больничные, отпуска и рабочая загрузка.
- Склад морозильных камер, аренда, показания счётчиков и история аренды.
- Отчёты по закрытым работам, P&L, закупки, комиссии и расходы.
- Excel-отчёт одним файлом с листами `Ремонты`, `Расходы`, `P&L`.
- Отчёт и график расхода фреона по месяцам.
- JSON-бэкап и расширенная Excel-выгрузка.
- Голосовое создание записей, клиентов и ремонтов, лимит записи 60 секунд.
- Telegram-уведомления и регистрация FCM-токенов.
- Светлая тема во всех основных вкладках.
- Мобильная навигация с кнопкой «Выйти» и вкладкой P&L.

## Реальные проблемы и незавершённые места

### Высокий приоритет
1. ~~**Самостоятельный выбор роли при первом входе.**~~ **Закрыто (2026-08-28).** `SetupView` больше не даёт выбирать роль (только имя), а `firestore.rules` при `create` в `staff` жёстко требует `role == "mechanic"` и запрещает смену своей роли/permissions. Роль меняет только admin/owner. Покрыто `firestore.rules.test.mjs`.
2. **Риск потери параллельных изменений — частично закрыто (2026-08-28).** Мутации массивов `clients/{id}.repairs|vehicles|chambers`, `servicetasks` и `freezers` переведены на транзакции с проверкой исходного снимка (`web/src/shared/firebase/concurrency.ts`, покрыто `firestore.concurrency.test.ts`): при конкурентном изменении бросается `ConcurrentMutationError` и пользователь получает alert. Остаётся архитектурный долг: ремонты по-прежнему хранятся вложенным массивом, отдельных документов нет — при высокой нагрузке стоит вынести ремонты/задачи в свои коллекции.
3. **Legacy appointments требуют отдельной миграции данных.** Все runtime-операции используют только глобальную коллекцию `appointments`; `client.appointments` читается только в карточке клиента для старых записей и никогда не изменяется. Однозначные старые dual-write копии скрываются по строгому точному сопоставлению, неоднозначные намеренно остаются видимыми. Массовая production-миграция не выполнялась.
4. **Финансовые месяцы считаются по дате начала ремонта.** Дашборд, P&L, отчёты и Excel в основном используют `repair.date`, а не `closedAt`. Из-за этого выручка может попадать не в месяц фактического закрытия; KPI «Закрыто сегодня» также использует неверное поле.
5. **Исторический P&L неточен.** Для прошлых месяцев используются текущие аренда камер, зарплаты и стоимость боксов; история изменения этих значений не учитывается.

### Средний приоритет
1. **Бэкап остаётся неполным.** JSON v2 сохраняет и восстанавливает глобальные `appointments`, однако по-прежнему не сохраняет `expenses` и `schedules`, не восстанавливает экспортированный `staff` и использует merge, поэтому не создаёт точный снимок.
2. **Возможен двойной учёт фреона в Excel.** Количество синхронно хранится в `repair.freonAmount` и `task.freonKg`, а экспорт в некоторых местах складывает оба значения.
3. **Удаление фото реализовано частично.** Отдельное удаление работает для фото задачи ремонта, но не для фото самостоятельных задач и подзадач. При удалении клиента, автомобиля, ремонта или задачи файлы могут оставаться в Firebase Storage.
4. **Telegram fallback не срабатывает при HTTP-ошибке.** Низкоуровневые вызовы логируют ошибку, но не выбрасывают её, поэтому заявленный текстовый fallback не запускается. Альбом также ограничивается первыми десятью фото без отправки следующих пачек.
5. **Автор фото в Telegram может быть неверным.** Используется `task.createdByName`, то есть создатель задачи, а не пользователь, фактически загрузивший фото.
6. **FCM реализован не полностью.** Токены регистрируются, но в проверенном backend-коде нет отправителя FCM. Локальное уведомление о росте числа задач работает только при открытой CRM. Абсолютный путь `/firebase-messaging-sw.js` может быть неверным для деплоя под `/app`.
7. **Дублируются модели и справочники.** `ServiceType`, модели записей и списки фреона объявлены в нескольких местах; значения `R404a/R404A`, `R507/R507a` различаются и могут дробить статистику.
8. **Недостаточная числовая валидация.** Закрытие наряда проверяет только непустую сумму; часть полей фреона и расходов допускает некорректные или отрицательные значения.
9. **Обработка ошибок непоследовательна.** Некоторые Firestore-операции не используют `try/finally`, из-за чего UI может остаться в состоянии сохранения, а пользователь не увидит понятного сообщения.
10. **Крупные монолитные компоненты, узкое покрытие тестами.** Критическая бизнес-логика смешана с UI в файлах на 1000–2200 строк (`ClientsTab` 2182, `DoneTab` 1737, `AppointmentsTab` 1436, `MyTasksTab` 1334, `StatsTab` 1263). Тесты сейчас покрывают только правила Firestore, appointments и конкурентные мутации; нет тестов для завершения задач, закрытия ремонта, финансовых периодов, фреона и Telegram diffing.
11. **Мобильное меню охватывает не все административные разделы.** В нём нет отдельных пунктов `Компании`, `Персонал` и `Бэкап`; компании доступны через переключатель внутри вкладки клиентов.
12. **Дизайн карточек ремонтов требует отдельной визуальной проверки.** Код обновлён, но субъективный пункт о «слипающихся» карточках нельзя считать подтверждённо закрытым без проверки интерфейса на целевых экранах.

## Правила, которые нельзя нарушать
- Тип транспорта автомобиля: только `Рефрижератор` или `Кондиционер`.
- Не путать тип транспорта с типом услуги ремонта: сейчас услуги дополнительно допускают `Морозильная` и `Другое`.
- При каждом новом ремонте автоматически создаётся задача «Заправка фреона».
- Дизайн основных экранов — светлая тема, белый/светло-серый фон.
- Секреты Telegram и другие приватные ключи нельзя добавлять в исходный код.
